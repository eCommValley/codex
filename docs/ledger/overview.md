# Codex Ledger overview

Codex Ledger CLI is a double-entry accounting assistant derived from the original Codex developer agent. The refactor swaps coding workflows for bookkeeping workflows while keeping the local-first execution model. Everything runs on your machine, leverages straightforward YAML/JSON data stores and integrates cleanly with Git for auditability.

## Architecture at a glance

```
project/
└── .ledger/
    ├── ledger.yml           # Company profile, chart of accounts, VAT profiles, policies
    ├── bank-transactions.json  # Imported statements awaiting classification
    ├── rules.json           # Deterministic categorisation and memo rules
    ├── journal.json         # Double-entry postings generated by `codex book`
    ├── audit.log            # Append-only record of every structural change
    └── exports/             # Optional directory for generated reports (user managed)
```

- **CLI layer** – `codex` dispatches to subcommands implemented in `codex-cli/src/commands`. Each command reads/writes the ledger data structures directly.
- **Core services** – helper modules handle YAML serialisation, CSV parsing, VAT math, period handling and audit logging.
- **Storage** – no database required. All files are human-readable to simplify reviews, code reviews and long-term retention policies.

## Operational principles

- **Local-first** – no data leaves your workstation. Sensitive inputs (bank statements, invoices, VAT returns) remain under your control.
- **Deterministic** – every journal entry is derived from explicit rules or manual decisions. There are no hidden LLM prompts or probabilistic actions in the accounting pipeline.
- **Audit ready** – the append-only `audit.log` records all significant CLI actions, while Git captures diffs of ledger files for long-term traceability.
- **Modular** – CSV/MT940 ingestion, VAT logic and reporting are isolated modules so that you can extend or swap them for jurisdiction-specific requirements.

## Key concepts

- **Chart of accounts** – defined in `ledger.yml`, including metadata such as type (asset, liability, income, expense) and optional VAT defaults.
- **Bank staging area** – imported transactions remain unbooked until `codex book` applies rules. Every transaction tracks origin file, row number and fingerprint.
- **Rules engine** – conditions describe how to recognise transactions (counterparty, description, amount range, direction). Postings define the destination account, VAT rate and memo template.
- **Journal entries** – each booking creates a balanced set of debits and credits, referencing both the originating transaction and the rule that triggered it.
- **Periods & locking** – closing a period appends a snapshot with ISO date bounds to prevent accidental rebooking.
